# Land Stack — Standard Technical Document (STD)

Version 0.1 · September 2026 · SIH 2026 problem statement "Land Stack" (GIS-based land-governance
platform). This document follows the section list the problem statement requires. Normative detail
lives in `docs/CONTRACTS.md` and in the code paths cited; this document explains the standards and
the reasoning.

## 1. System architecture

Land Stack is a **parcel-centric integration platform**: the ULPIN-style parcel id is the join key
across every department, and no department's data is copied into another's schema. Six department
services (revenue, registration, planning, fiscal, legal, utilities) are independent FastAPI
applications (`apps/api/departments/<name>/app.py`), each reading and writing **only** its own
PostgreSQL schema `dept_<name>` and speaking its own vocabulary (RoR/khata, deed/encumbrance,
zone/permit, assessment/valuation, case, connection). A **gateway** (`apps/api/landstack`) exposes
the public API, authenticates users, calls the departments through *adapters*
(`landstack/adapters/*.py` + YAML field mappings) and merges the answers into one Common Data Model
per parcel with per-source provenance, latency and consistency findings (`services/aggregator.py`,
`services/consistency.py`). Departments push change events back (`POST /landstack/events`,
`X-Events-Secret`) via a transactional outbox, so a deed registered in the registration system can
open a system-initiated mutation in revenue within seconds.

Physically the prototype is one container: the department apps are mounted inside the gateway
process and called over an in-process ASGI transport (`DEPT_BASE_URL` empty). Setting
`DEPT_BASE_URL` to a host switches the adapters to real HTTP with the same contract, which is how a
state would point the gateway at Meebhoomi / IGRS / DTCP endpoints. The web client
(`apps/web`, Vite + React 19 + TypeScript, MapLibre GL, TanStack Router/Query, Zustand, ECharts) is
a static SPA served by Firebase Hosting; the API runs on Cloud Run; the database is PostgreSQL 16 +
PostGIS on Neon; signed PDF reports go to Cloud Storage; Firebase Auth issues identity tokens.
See the Mermaid diagram in the root `README.md`.

## 2. Data schemas

**Three-state data model.** `landstack.parcels.state` ∈ {AP, TN, TG}; `dept_revenue.ror.state`
(migration 007) selects the dialect each RoR row is served in; `gis.settlement_schemes`
(migration 006) holds each state's resurvey-programme areas (phase: notified/in_progress/completed)
and parcels carry the matching `status_flags.resurvey`. Buildings carry footprint width/depth and
`basement_floors` (migration 010).

The database is split into eight schemas applied by idempotent SQL migrations
(`db/migrations/001_extensions.sql` … `005_views.sql`, run by `tools/migrate.py` in filename order and
recorded in `landstack.schema_migrations`):

| Schema | Tables | Role |
|---|---|---|
| `landstack` | parcels, buildings, units, users, consents, applications, transitions, audit_log, alerts, reports, connector_status, schema_migrations | Platform core: cadastre geometry, 3D units, workflow, audit, alerts, signed reports |
| `dept_revenue` | ror, mutations | Record of Rights (khata) and mutation ledger |
| `dept_registration` | deeds, encumbrances, outbox | Registered instruments, charges, event outbox |
| `dept_planning` | zones, building_permissions | Master-plan zoning and permits |
| `dept_fiscal` | property_tax, valuation | Tax demand/arrears, guideline value |
| `dept_legal` | disputes | Court cases against parcels |
| `dept_utilities` | connections | Water/electricity/sewer/road access |
| `gis` | roads, water_lines, restriction_zones, projects, village_boundary, s2_change | Reference layers and Sentinel-2 change indices |

Conventions: every geometry column is `geometry(<Type>, 4326)` with a GiST index; areas are computed
as `ST_Area(geom::geography)` in m²; free-text search columns (`parcels.survey_no`, `ror.owner_name`)
carry `pg_trgm` GIN indexes; JSONB is used only for open-ended payloads (`applications.payload`,
`audit_log.before/after`, `parcels.status_flags`). The view `landstack.parcel_status` derives the
map/KPI flags (registered, dispute, mortgage, arrears, pending mutation, permission status, change
alert) and `landstack.parcel_tile_features` feeds the vector tiles. Identifiers: `ulpin` (14-char,
geohash + geometry hash, `services/ulpin.py`), 3D units `<ULPIN>-F<floor:02>-U<unit:02>`, applications
`APP-<year>-<seq:06>`. The gateway-facing **Common Data Model** (`landstack/cdm.py`, mirrored in
`apps/web/src/lib/cdm.ts`) has the blocks `identifiers · spatial · party · rights · restrictions ·
planning · fiscal · utilities · buildings · alerts · provenance · consistency · status`; its JSON shape
is fixed in CONTRACTS §5.

## 3. API standards

All endpoints are HTTP/JSON with OpenAPI 3.1 documents generated by FastAPI (`/docs`, `/openapi.json`,
plus one per department at `/<dept>/docs`). Errors use one envelope
`{"error": {"code", "message", "details"}}` (`landstack/errors.py`); every response carries
`X-Request-ID` and `X-Response-Time-Ms`; department responses carry `X-Source-System` and an `as_of`
timestamp. Authentication is `Authorization: Bearer <Firebase ID token>`; roles come from custom
claims and are enforced by `require(*roles, department=)` dependencies.

Gateway surface (`apps/api/landstack/routers/`): **meta** `GET /healthz`, `GET /`; **auth** `GET
/landstack/me`; **collections (OGC API – Features style)** `GET /landstack/collections`,
`/{layer}`, `/{layer}/items?bbox&limit&offset&land_use&status`, `/parcels/items/{ulpin}`; **tiles**
`GET /landstack/tiles/{layer}/{z}/{x}/{y}.pbf`; **search** `GET /landstack/search?q=`; **parcels**
`GET /landstack/parcels/{ulpin}`, `/{ulpin}/timeline`, `POST /landstack/verify-ownership`;
**applications** `POST/GET /landstack/applications`, `GET /applications/{id}`, `POST
/applications/{id}/transition`, `GET /landstack/queue`; **stats** `GET /landstack/stats`; **alerts**
`GET /landstack/alerts`, `POST /alerts/{id}/assign|resolve`; **consistency** `GET
/landstack/consistency`; **connectors** `GET /landstack/connectors`, `GET /landstack/adapters`;
**events** `POST /landstack/events`; **reports** `POST /landstack/reports/{ulpin}`, `GET
/reports/{id}.pdf`, `GET /verify/{id}`; **consents** `POST /landstack/consents/request|grant`, `GET
/landstack/consents`; **admin** `POST /landstack/admin/simulate/deed`, `/demo-reset`,
`/cache/invalidate`; **ai** `POST /landstack/ai/change-detection`, `/extract-document`. Department APIs
(CONTRACTS §7) are deliberately heterogeneous to prove the adapter layer. Pagination is
`limit/offset`; filters are query parameters; writes are POST with Pydantic-validated bodies;
state changes are explicit `transition {action, remark}` calls governed by the `transitions` table.

### 3.x AI assistance endpoints

`POST /landstack/ai/parcel-brief` (any signed-in) and `POST /landstack/ai/application-advice`
(officer+) provide risk briefs and next-action recommendations. Generation runs on NVIDIA Build
(OpenAI-compatible chat completions; `NVIDIA_MODEL`, default `nvidia/nemotron-3-super-120b-a12b`) when
`NVIDIA_API_KEY` is configured, and on a deterministic rule engine otherwise; every response carries
an `engine` field and the UI labels the provenance. The model receives only a compact fact sheet
derived from the caller's own (masked) CDM view. Document extraction
(`POST /landstack/ai/extract-document`) prefers the NVIDIA vision model.

### 3.y Bounded boundary correction

`POST /landstack/parcels/{ulpin}/boundary/validate` and `POST .../boundary` implement bounded
parcel-geometry editing: validity, 4–200 vertices, |Δarea| ≤ 15%, no overlap > 1 m², containment in
the village boundary, plus an assistive snap/overlap-subtraction suggestion. Proposals flow through
the `boundary_correction` workflow (submitted → geometry_check → approved/returned/rejected, revenue
officer); approval re-validates, applies the geometry, recomputes the area and syncs the RoR extent
(revenue `POST /extent`). All steps are audited.

**GIS overview (three regions).** The demo spans three real bounding boxes — Mangalagiri (AP),
Sriperumbudur (TN), Shamshabad (TG) — ~150 thinned parcels each; the map serves a national
overview (cluster markers below z8, parcel tiles z10+) and per-region village boundaries.

## 4. Interoperability standards

- **Identifiers**: ULPIN-style 14-character ids for parcels (DILRMP-compatible shape); 3D suffixes for
  floors/units anticipating the 3D-ULPIN extension; ISO 8601 UTC timestamps; EPSG codes for CRS.
- **Geospatial exchange**: OGC API – Features conventions for `collections/*/items` (GeoJSON, bbox
  filter, limit/offset), Mapbox Vector Tiles (MVT v2, `application/vnd.mapbox-vector-tile`) at
  XYZ addresses, GeoJSON for import/export, Cloud-Optimised GeoTIFF for imagery; the schema is also
  directly servable by martin/pg_tileserv and consumable by QGIS.
- **Department integration**: REST/JSON adapters with declarative YAML field mappings
  (`adapters/mappings/*.yaml`) so a new source system is a mapping file plus base URL; event-driven
  sync via a transactional outbox and a signed webhook (`X-Events-Secret`) with event names
  `registration.deed_registered`, `revenue.ror_updated`, `planning.permission_issued`; per-call timeouts
  (`DEPT_TIMEOUT_S`) and cached-last-good fallbacks surfaced in `provenance`.
- **India Stack alignment**: consent-token based data sharing (`landstack.consents`) mirrors the
  DEPA/Account-Aggregator consent pattern; roles map to e-Pramaan style departmental identities;
  masked public views follow the "open by default, personal data by consent" principle of the
  National Data Sharing and Accessibility Policy. Bhuvan WMS can be layered behind a flag.
- **Documents**: verification reports are PDF/A-style with a QR code that resolves to a public
  `GET /verify/{id}` JSON endpoint, so third parties verify without an account.

### 4.x The per-state adapters are the interoperability proof

The claim "onboarding a state is a mapping file, not a migration" is backed by code:
`adapters/mappings/revenue_ap.yaml` (Meebhoomi vocabulary: khata_no/owner_name/extent_sqm),
`revenue_tn.yaml` (Patta Chitta: patta_no/pattadar_name/extent_hectares) and `revenue_tg.yaml`
(Dharani: ppb_no/pattadar_name/extent_acres) translate three live dialects into the same CDM,
with unit conversion (hectare/acre → sqm) declared in the mapping. The registry selects the
mapping per parcel state at request time; unmapped departments fall back to the AP mapping.

## 5. GIS standards

Storage and API CRS is **EPSG:4326** (WGS 84) as mandated for national interoperability; geometry is
generated and measured in a projected CRS (EPSG:32644, UTM 44N) so areas and lengths are in metres,
and coordinates are stored at 7-decimal precision (~1 cm). Parcels are `MultiPolygon`, buildings
footprints `MultiPolygon`, units `Polygon` with `base_m/height_m` for extrusion, roads/water
`LineString`. Validity is enforced with `ST_MakeValid` on ingest; topology rules (no parcel overlap
within a village, parcels within the village boundary) are checked by the consistency service and
reported rather than silently fixed. Tiles are produced server-side with `ST_AsMVT` from the
`parcel_tile_features` view, zooms 10–20, with feature ids = ULPIN so the client can use
feature-state for hover/selection. The map follows the three-tier layer model of the problem
statement: Tier 1 base (parcels, survey labels, village boundary, basemap switch — vector, or Esri
World Imagery with attribution), Tier 2 essential (parcels recoloured by land use, ownership type,
registration, encumbrance, dispute, zone, permission), Tier 3 use-case (tax arrears, guideline value,
roads, water lines, restriction zones, projects, change alerts). Change detection uses Sentinel-2
L2A NDVI/NDBI differences per parcel (`apps/api/ai/change_detection.py`) with offline COGs for
demos and Microsoft Planetary Computer online.

## 6. Security framework

Identity is delegated to Firebase Authentication (Google and Email/Password providers); the API
verifies ID tokens with firebase-admin and reads `role ∈ {citizen, officer, admin}` and `department`
from custom claims set only by administrators (`tools/set_claims.py`). Authorisation is enforced at
the route level with `require(...)` and at the data level by **masking** (`services/masking.py`):
citizens see owner names as initials, no father's name and only the last four characters of deed
numbers unless a time-boxed consent exists. Every state change is written to an append-only
`audit_log` (actor, before/after, source). Department → gateway webhooks require a shared secret;
report PDFs are hashed (SHA-256) and signed with HMAC-SHA256 so `GET /verify/{id}` proves integrity.
Transport is TLS everywhere (Firebase Hosting, Cloud Run, Neon `ssl=require`). Secrets live in
Secret Manager and are injected as environment variables; the container runs as a non-root user;
CORS is an explicit allow-list; SQL uses bound parameters only. The dev-mode `X-Dev-User` header is
honoured solely when `AUTH_MODE=dev` and is never enabled in the cloud deployment. Static hosting
sets `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy` and `Permissions-Policy`.

## 7. UI/UX guidelines

The interface is task-first: a citizen lands on **search → parcel profile → act** (verify
ownership, track, request), an officer on **KPIs → queue → application detail with the allowed
transitions only**, an administrator on **connectors → mappings → findings → simulate**. The map is
the shared canvas; the Parcel Profile drawer opens beside it so spatial and record context are
never separated. Every screen works with keyboard and screen reader (semantic HTML, focus rings,
ARIA on tabs/drawer), meets WCAG 2.1 AA contrast in both light and dark themes, and degrades to a
single column at 360 px. Loading and error states are explicit (skeletons, provenance chips showing
which department was slow or unavailable). Language is plain and bilingual-ready (labels sourced
from one dictionary); numbers use Indian grouping and units are always shown (m², ₹). Destructive or
legal actions (approve, reject, grant consent) require a remark and show the audit consequence.
Components are small Tailwind v4 primitives (`apps/web/src/components`: Button, Card, Badge, Tabs,
Drawer, Field) to keep visual and behavioural consistency.

## 8. Colour schema

Tokens are defined once in `apps/web/src/styles.css` and exposed to Tailwind via `@theme`; the map
style (`features/map/styles/layers.ts`) uses the same semantic colours so legend and UI agree.

| Token | Light | Dark | Meaning |
|---|---|---|---|
| `ground` / `panel` | `#f6f5f0` / `#ffffff` | `#14181a` / `#1e2427` | page background / surfaces |
| `ink` | `#1d2320` | `#e6e8e4` | text |
| `line` | `#d9d6cb` | `#2f373b` | borders |
| `primary` | `#0e6b54` | `#4fc39f` | actions, selection, "registered / clean" |
| `amber` | `#9a6b12` | `#d9a441` | pending, arrears, caution |
| `brick` | `#a63a2b` | `#e0705f` | dispute, change alert, rejected |
| `violet` | `#6b4e9a` | — | encumbrance / mortgage |
| `slate` | `#2f5d9e` | — | planning zones, informational |

Map categorical palettes (land use, ownership type, zone class) are colour-blind-safe and limited to
seven hues; status layers use the semantic tokens above; the neutral parcel fill is `#B9B5A6` at
40–75 % opacity depending on hover/selection, and lines switch to white over imagery.

## 9. Deployment & scalability

**Environments**: local (`infra/docker-compose.yml`: PostGIS 16-3.4, one-shot migrate+seed, API with
hot reload, Vite dev server, optional nginx and martin profiles); CI (GitHub Actions: ruff, migrations
+ seed against a PostGIS service container, pytest with integration tests, TypeScript typecheck and
production build, `pglast` parse of every migration, compose/firebase config sanity); cloud (Firebase
Hosting for the SPA, Cloud Run `landstack-api` in asia-south1 with 512 MiB, concurrency 80, 0–3
instances, Secret Manager, Cloud Storage for reports, Neon serverless PostGIS). Deployment is
`make deploy-api` (Cloud Build from `infra/cloudrun/cloudbuild.yaml`, `gcloud run deploy`) and
`make deploy-web` (`firebase deploy --only hosting`); `infra/cloudrun/service.yaml` is the equivalent
Knative manifest for GitOps.

**Scalability path**: the gateway is stateless (per-instance CDM cache with TTL, invalidated on
events), so Cloud Run scales horizontally by raising `max-instances`; PostGIS tiles can be cached at
a CDN or pre-rendered to PMTiles for static layers; department sub-apps can be split into their own
services by setting `DEPT_BASE_URL` without code changes; Neon scales compute independently of
storage and supports read replicas for tile/read traffic; migrations are forward-only and idempotent
so blue/green revisions are safe. For a state-wide rollout the same layout maps onto MeghRaj/NIC
cloud (Kubernetes + managed PostgreSQL) because every component is a standard container with
twelve-factor configuration. Cost at prototype scale is within free tiers (see
`infra/cloudrun/README.md`); the demo recovers to a known state in under 30 s with
`tools/demo_reset.py`.
