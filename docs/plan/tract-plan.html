SIH 2026 · PS SIH26014 · Dept. of Land Resources

Land Stack Build Plan

A parcel-centric GIS platform where one click on a land parcel returns everything government knows about it — ownership, registration, tax, zoning, permissions, encumbrances, utilities — assembled live from separate department APIs through a single ULPIN-style key. This is the plan to build a working prototype in seven days with a six-person Python + JavaScript team.

Build window 7 days Team 6 (3 Python, 3 JS) Demo target local docker-compose + public URL Status plan v1 · 13 Sep 2026

1 · What the problem statement actually grades

The PS title is "An Integrated GIS-based Digital Public Infrastructure for Land Governance" (SIH26014, Ministry of Rural Development / DoLR, Software, theme Agriculture, FoodTech & Rural Development). Reading the text, judges are asked to look for six concrete things. Everything in this plan traces back to one of them.

Context worth saying out loud in the pitch. DoLR launched the real Land Stack pilot in Chandigarh and Tamil Nadu on 31 December 2025. The Chandigarh portal was built by NIC in about six months and shows per-parcel property, ownership, deed, encumbrance and litigation. Our differentiator is not the map — it is the open interoperability layer: standards-based APIs, a state-configurable adapter model, and consent-aware citizen access, which the pilot does not expose. Frame the whole project as "the API layer Land Stack needs to scale from 2 pilots to 36 states/UTs".

3 · Product surfaces

One React app, one route tree, five surfaces plus a satellite panel. Roles decide what a user lands on after sign-in; the map is shared by all.

Map Explorer all roles

Full-bleed MapLibre map. Left panel: layer tree in the PS's three tiers with toggles and legends. Top: search (ULPIN, survey no., owner name). Hover highlights a parcel and shows a mini-card; click opens the Parcel Profile drawer. Colour-by mode: land use, status (verified / disputed / mortgaged / pending), tax status, change-detection alert.

Parcel Profile all roles, consent-masked

The aggregated record, sectioned by department with a source badge and "fetched at" timestamp on each block. Tabs: Overview · Ownership & RoR · Registration & Encumbrance · Planning & Permissions · Fiscal · Utilities · Timeline (audit) · Satellite. Citizens see owner name masked (R*** K****) unless they hold a consent token; officers see full detail.

Citizen Portal citizen

Four cards mirroring R4: Search parcel · Verify ownership · Track application · Request a service. Service forms: Mutation (transfer of RoR) and Building Permission. Every submission gets an application ID, a status timeline and a downloadable PDF report with QR.

Officer Console officer (revenue / registration / planning)

KPIs (total parcels, verified %, pending, disputed, mortgaged, tax arrears), land-use breakdown, a filterable map, and a work queue of applications routed to this officer's department. Approve / return / reject with a mandatory remark; every action writes to the audit log.

Admin & Integration Console admin

Connector grid (Revenue, Registration, Planning, Fiscal, Legal, Utilities, Satellite) with health, latency and last sync; the common-data-model field mapping per adapter; the consistency checker's findings; and a "Simulate upstream change" button used in the demo.

Satellite panel officer / admin

For a parcel or a selected area: two Sentinel-2 dates side by side, NDVI/NDBI Δ, a classified label (vegetation → built-up, etc.), a confidence value and a "Send for field review" action that creates a task in the work queue.

4 · Architecture

Three planes: a client, a gateway that owns identity, aggregation, workflow and audit, and a set of department services that each own their own tables — deliberately separate so we can show one of them changing and the gateway noticing. Everything runs from a single docker compose up.

Solid green arrows are synchronous fan-out on a parcel request (parallel httpx calls, 300 ms budget, partial results allowed with a per-block "source unavailable" state). The dashed arrow is the asynchronous event path used in the sync demo. Department services are separate FastAPI sub-applications in the same process for the hackathon; in production each becomes an adapter to a real state system, which is why they only ever talk to the gateway through HTTP and never share tables.

Why one process, six apps

Judges reward visible interoperability, not container count. Mounting /revenue, /registration, /planning, /fiscal, /legal, /utilities as sub-applications gives six independent /docs pages and six independent schemas while keeping a single uvicorn to debug. Each sub-app writes only to its own Postgres schema, enforced by a per-schema database role, so the separation is real even though the process is shared.

6 · Data model

The centre of the system is a common data model (CDM) for a parcel. Departments store data in their own vocabulary; adapters map into the CDM; the UI only ever renders the CDM. The field groups map onto ISO 19152 LADM's Party / RRR / Spatial Unit split, which is worth citing because the PS's "ownership, rights, restrictions, liabilities" wording is LADM language.

ULPIN-style identifier

Real ULPIN (Bhu-Aadhaar) is a 14-character ID derived from parcel vertex coordinates under ECCMA's PNIU scheme; the exact derivation is not public. For the prototype we generate a deterministic 14-character ID from the parcel geometry and label it "ULPIN-style" everywhere, which is honest and still demonstrates the key property: the ID is a function of where the land is, not of any department's register.

def ulpin_style(geom_wgs84) -> str:
    c = geom_wgs84.centroid
    gh = geohash.encode(c.y, c.x, precision=7)               # 7 chars, ~150 m cell
    h  = blake2b(geom_wgs84.wkb, digest_size=4).hexdigest()  # 8 hex chars from vertices
    return (gh + h).upper()[:14]                             # e.g. TDR1K3M9A2F7C1

7 · GIS pipeline and the three layer tiers

Where the parcels come from

There is no open parcel-level cadastral dataset for India; this was verified, and it is why the PS says mock data is acceptable. The honest and fast route is to synthesise a realistic cadastre inside a real village boundary so the map sits on real roads and real imagery.

  1. Take one village polygon from the DataMeet Indian Village Boundaries dataset (EPSG:4326) — pick a peri-urban village next to a town so the satellite change-detection story has genuine construction between 2019 and 2025 (e.g. a village on the Amaravati or Hyderabad ORR fringe). Add an adjacent urban ward drawn from OSM landuse polygons.
  2. Pull OSM roads for the area (Overpass) and use them to split the village polygon into blocks (shapely.ops.split, then polygonize).
  3. Subdivide each block into parcels with a jittered Voronoi or recursive strip split in a projected CRS (EPSG:32644 for AP/TS, 32643 for Karnataka/TN west) so areas are honest; target 400–800 parcels with a realistic size distribution (60–400 m² urban, 0.2–2 ha agricultural).
  4. Assign survey numbers (123, 123/1, 123/2A) following the Indian sub-division convention, land use by distance to road and to the town, owners via Faker with Indian locales, and 5–8 % anomalies: disputes, mortgages, tax arrears, area mismatches across departments, pending mutations.
  5. Write landstack.parcels and populate every dept_* table from the same seed frame, then deliberately break a few rows (owner spelling drift, extent ±8 %) so the consistency checker has real findings.

This is one Python script (tools/seed.py, GeoPandas + Shapely + Faker), idempotent, run by make seed. It should take under two minutes and finish before Day 2 ends, because everyone else is blocked on it.

CRS rules

Store and exchange in EPSG:4326 (GeoJSON RFC 7946 requires it). Compute area, length and buffers in the local UTM zone (EPSG:32643 / 32644) or with geography casts. State the caveat in the technical document that real Indian cadastral sheets sit on state-specific Lambert Conformal Conic / Everest datums and that a production adapter must reproject on ingest.

Aggregator behaviour

async def get_parcel(ulpin, caller):
    base = await repo.parcel(ulpin)                           # PostGIS, always available
    tasks = { name: adapter.fetch(ulpin) for name, adapter in registry.items() }
    results = await gather_with_timeout(tasks, timeout=0.3)   # partial results allowed
    cdm = merge(base, results)                                # adapters already emit CDM fragments
    cdm.consistency = check(cdm)                              # area / owner match across sources
    if caller.role == "citizen" and not caller.has_consent(ulpin):
        cdm = mask(cdm)                                       # names → initials, doc numbers → last 4
    return cdm

9 · Interoperability layer

This is the part of the project that answers "how does this work in Tamil Nadu and Andhra Pradesh?" and it is deliberately small: an adapter interface, a field-mapping config per source, and an event contract.

    name: str                       # "revenue"
    async def fetch(self, ulpin: str) -> CDMFragment: ...
    async def health(self) -> Health: ...
    def mapping(self) -> dict[str, str]: ...   # source_field → cdm_field, shown in Admin console

11 · The AI feature: satellite land-use change detection

Pick one AI feature and make it unmissable. Change detection was chosen over OCR because it is visual, ties directly to the map, generates work for the officer queue, and can be made fully deterministic and offline. The method is index differencing, not a neural network, and that is a feature: it is explainable to a revenue officer in one sentence.

Method

  1. Search Sentinel-2 L2A on the Planetary Computer STAC for the AOI bbox, two windows (e.g. Jan–Mar 2019 and Jan–Mar 2025, dry season), cloud cover < 10 %. Pick the least-cloudy scene per window.
  2. Load bands B04 (red), B08 (NIR), B11 (SWIR) at 10–20 m with odc-stac, clipped to the AOI. Sign asset URLs with planetary_computer.sign(); no key required for Sentinel-2.
  3. Compute NDVI = (B08−B04)/(B08+B04) and NDBI = (B11−B08)/(B11+B08) for both dates.
  4. Zonal mean per parcel with rasterstats; ΔNDVI and ΔNDBI per ULPIN.
  5. Classify: ΔNDVI < −0.20 and ΔNDBI > +0.10 → "vegetation → built-up"; ΔNDVI < −0.20 only → "vegetation loss"; ΔNDBI > +0.15 only → "new construction"; else "no significant change". Confidence = clipped normalised magnitude of the combined Δ, reported as a percentage with the thresholds shown.
  6. Cross-check against the record: a parcel classified as built-up whose RoR says agricultural, with no building permission on file, becomes a change_detected alert with severity high and a "Send for field review" action.

Offline guarantee

On Day 2–3 the AI owner downloads the two clipped scenes as Cloud-Optimised GeoTIFFs into data/s2/ and commits the resulting per-parcel Δ table to the seed. With OFFLINE=1, the endpoint reads local files and returns in under a second. The demo runs in offline mode; the online path is shown only if the venue network holds up.

Optional second feature: document extraction

If change detection is stable by Day 5 evening: an officer uploads a scanned RoR (Telugu or Hindi); the file goes to Gemini Flash with a Pydantic schema (survey_no, owner_name, extent, classification, each with confidence); the JSON is shown side by side with the scan for one-click acceptance into dept_revenue.ror. Tesseract with tel/hin traineddata sits behind a flag as the no-internet path. Pre-cache the three demo documents' results so the stage demo never waits on the API.

15 · Demo script (6 minutes)

One story, one parcel family, no tab-hunting. Rehearse the words as much as the clicks.

  1. The problem (30 s). Show the Admin console's connector grid with six disconnected systems. "Today Ravi visits six offices to learn one thing about one plot."
  2. The map (45 s). Open Map Explorer over the village on satellite imagery. Toggle the three tiers in order — base, essential, use-case — naming them as the PS does. Switch colour-by to "status" so disputes and mortgages pop.
  3. One click (60 s). Click parcel 123/4. Walk the profile: ownership from Revenue, deed from Registration, zone from Planning, tax from Fiscal, no disputes, utilities present — point at the source badges and the as_of times. Open Timeline.
  4. Interoperability, live (45 s). In the Registration mock, register a sale deed on 123/4 to Lakshmi Devi. Switch back: the parcel turns amber, the profile shows the mismatch banner, and the revenue officer's queue has a system-initiated mutation. "That is the Kaveri-to-Bhoomi hand-off, done through an open event contract."
  5. Citizen service (45 s). As Lakshmi (citizen), verify ownership (masked result), track the mutation, download the signed Land Information Report and scan the QR on a phone to verify it.
  6. Officer decision (30 s). As the revenue officer, approve the mutation with a remark; the RoR updates, the map returns to green, the audit trail shows both machine and human steps.
  7. AI (60 s). Open the Satellite panel on the neighbouring parcel 124: 2019 vs 2025 imagery, NDVI −0.31, NDBI +0.18, "vegetation → built-up, 91 %". The record says agricultural with no building permission; send for field review. Show the resulting alert on the map layer.
  8. Resilience & scale (30 s). Flip the fiscal service to fail; reload the profile; the fiscal block shows "source unavailable, cached 2 h" while everything else loads. Close on the Standard Technical Document and the OpenAPI pages: "six systems, one key, open standards."

17 · Standard Technical Document — what it must contain

R6 lists the sections by name. Use exactly these headings so the evaluator can tick them off.

1 · System architecture

The diagram in §4, the three planes, sync vs async paths, one-process-six-apps rationale, production topology (adapters per state, gateway per state or central).

2 · Data schemas

CDM JSON Schema; table DDL from §6; LADM mapping; ULPIN-style derivation; DoLR Glossary of Revenue Terms used for field names (khata, patta, khasra, survey no.).

3 · API standards

OpenAPI 3.1 for all seven apps (exported); OGC API Features conventions for collections/items; versioning (/v1), pagination, error envelope, idempotency keys on POST.

4 · Interoperability standards

Adapter interface and YAML mapping; event contract; API Setu / DEPA consent alignment; MeitY MDDS codes for state/district/village; NGDRS as the precedent for push-based registration data.

5 · GIS standards

GeoJSON RFC 7946, EPSG:4326 exchange / UTM 43N-44N computation, MVT spec, WMS 1.3 / WFS 2.0 consumption (Bhuvan), topology rules (no overlaps, no gaps), metadata per layer (source, date, accuracy).

6 · Security framework

JWT/RBAC matrix from §12, consent tokens, append-only audit, PII masking rules, report signing, TLS, rate limits, OWASP ASVS L1 as the baseline checklist.

7 · UI/UX guidelines

Role-first navigation, map as shared canvas, provenance always visible, plain-language status names, bilingual labels (English + state language) as a design rule, WCAG 2.2 AA contrast.

8 · Colour schema

Status colours (verified green, pending amber, disputed red hatch, mortgaged violet, government blue), land-use palette, zone palette, alert severities — with hex values and a colour-blind-safe check.

9 · Deployment & scalability

docker-compose for dev; Kubernetes sketch for a state (gateway HPA, PostGIS with read replicas, Martin behind CDN, PMTiles nightly above 5 lakh parcels, Redis, object storage); rollout from 1 village → 1 district → state; cost notes.
